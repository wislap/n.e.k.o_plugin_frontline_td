## 1. 阶段与路线图

### 1.1 目标
交付 **可玩的原型 + 扎实的开发框架底座**，供开源小团队（NEKO 插件开发者）评审后再提意见。工期充足，质量优先于速度。

原型范围：一张固定地图。MVP（M1–M4）参照团队《设计决策清单 v2》A6（2026-11-15，非正式需求；条目转写见 [ADR 0033](../adr/0033-design-checklist-referenced-items.md)）：网格地图 + 矿机 + 一种生产建筑 + 建造需物资送达；单层物流网（ADR 0025）；小队驻守 / 推进两种状态；一个敌方集结点 + 一次反攻 + 路线箭头；单摄像机 3D 观战 / 正交指挥切换；无界面对拍工具 + 4 个策略机器人 + 状态哈希测试；另加一种基础炮塔。M5 补齐底座玩法（攻占据点、敌方基地、迷雾、局外占位）。灰盒美术。

## 2. 背景

- 项目是 NEKO 插件。现阶段 **NEKO 插件系统只是启动器**：游戏本体是打包好的网页游戏，跑在插件面板的 iframe 中。参考项目 `neko_survivors`（React + TS + PixiJS，规则跑在 Web Worker，Python 只做薄壳）。
- 团队是开源小团队，成员默认都是 NEKO 插件开发者，普遍使用 AI 辅助编程（vibe coding）。
- 玩法设计以 `game_design.md` 为准，但它不是不可动摇的需求：【已定】是当前采用的方案，负责人本人也不认可其中全部内容；【建议】【待定】需要先确认再实现（见该文档开头的「本文的地位」）。
- 本文的核心关切：**中大型项目在 vibe coding 环境下如何长期开发、协作、维护**。加功能很廉价，架构、规范、可维护性才是重点。

## 3. 约束

### 3.1 运行环境
- 产物是纯静态网页，以 `mode = "static"` 面板加载 `static/index.html`。宿主为 NEKO（Electron / Chromium），WebGL2 可用。
- 开发时也可用 `npm run dev` 在浏览器中单独运行（热更新），但不是硬性要求。
- 插件包只包含构建产物；运行时没有 npm。Python 只是薄壳，不参与游戏逻辑。
- 插件面板有 normal / focus / fullscreen 三种模式，渲染与 UI 必须适配尺寸变化；模式切换经宿主 SDK 由用户触发（[ADR 0032](../adr/0032-host-display-autopause.md)，启动时不主动请求）。
- 窗口隐藏时 rAF 停止、Worker 计时器被节流，因此 `visibilitychange` 隐藏时自动暂停（不自动恢复，ADR 0032）。NEKO 宿主隐藏插件面板时是否会触发 `visibilitychange` 尚未实测。

### 3.2 平台与规模
- 只做 PC 键鼠单机。不写联机代码；确定性 + 命令协议为将来的 lockstep（例如 PVP）留出余地。不做触屏。
- 当前版本只有攻占模式；PVP、对称 AI、感染模式等是可能的方向，随时可能加入或删掉（`game_design.md` §4.9）。
- 规模按大地图、大量单位设计（具体数值随地图设计变化，按上限考虑）。
- 性能基准硬件：RTX 5060。先实现，再根据实测优化。

### 3.3 模拟
- 固定步长，每 tick 推进 **50ms 模拟时间**，1x = 20Hz。
- 必须支持变速与暂停。倍速档位初始为 `[0, 1, 2, 3]`，以配置数组定义。
- 必须确定性（见第 9 节）。
- 模拟层禁止直接使用超越函数，统一使用自有确定性实现（原因：CI 的 Node 与 NEKO 的 Electron V8 版本不同，且会随升级变化）。

### 3.4 地形
- 不是平面：有空中层、城墙、高地，将来可能有海域、悬崖等。高度进入规则（视线、射程修正），不只是视觉（尚未实现，见 ADR 0010、0011）。

### 3.5 内容与地图
- 原型自带 1 张固定地图；将来一关一张地图，地图来源多样（手工、生成、外部工具导入等）。
- 弹道类型多样（例如光束、延迟但必定命中、范围炮击），不能写死为枚举。
- 建造有进度、消耗资源。

### 3.6 多语言
- 必须支持，禁止硬编码用户可见文本。先做 zh-CN 与 en。
- 插件元数据的 i18n（`plugin.toml` 的 `[plugin.i18n]`）在有需要时再加。

### 3.7 存档与版本
- 原型不做存档（原型只有一局、一张地图，没有关卡之上的进度）。但模拟状态必须始终可完整序列化，保证以后加存档只涉及 UI 与存储层。
- 地图、内容、回放格式从第一天起带 `formatVersion`。回放只保证同一构建内有效；存档跨版本需迁移或声明不兼容。

### 3.8 许可证
- 首选 MIT；必要时可接受 GPL。
- 已核实（2026-11-14）：NEKO 主仓库为 Apache-2.0；three、@react-three/fiber、zustand、react、dependency-cruiser 为 MIT；bitecs 为 MPL-2.0（文件级弱 copyleft，作为未修改的依赖使用不影响 MIT）。

### 3.9 协作与环境
- 跨平台开发（Windows / macOS / Linux）：`.gitattributes` 统一 LF；`engines` + `.nvmrc` 固定 Node 版本；包管理器 npm。
- 文档正文用中文；代码标识符、代码注释、提交信息用英文。
- 插件目录是嵌套 git 仓库（`plugin/plugins/frontline_td/`），GitHub 仓库名 `n.e.k.o_plugin_frontline_td`。
- 下一步候选事项维护在 §1.4；具体任务的共享计划走 GitHub issue + 开发群通知，不进仓库。

## 4. 诉求

1. **模块化，改动可控**：改一个子系统、加一个功能时，其他系统的改动可预测、局部化。
2. **数据结构与分层严格**，由工具强制，不靠自觉。
3. **长期可维护**：防止项目被"许愿式 vibe coding"逐渐腐化到不可控。
4. **文档分层**：长期文档给人和 agent 读、动手前必读；施工计划做完即扔，不进主分支。
5. **可复现、可测试**：bug 可用种子 + 命令序列复现；玩法机制有可执行的验收标准。
6. **为将来留接口但不提前实现**：平衡调试工具、存档、多地图、3D 观战、NEKO 解说。
7. **玩法可增删**：以后加入或删掉某种玩法（PVP、对称 AI、感染模式等）时，既有架构不能成为阻碍；删除一种玩法不应牵动通用模块。

## 6. 架构

### 6.1 模拟层的含义
模拟层是 **无头游戏核心**：游戏规则本身，不依赖画面、DOM、React、three、zustand。对外只有两个口：**命令进，快照 / 事件出**。渲染与 UI 是它的观察者和输入设备。它借用了客户端 / 服务端分离的思想，但所有代码都在本地运行，没有网络。

```text
玩家操作 ──命令──▶ 模拟层（Worker，固定 tick） ──快照 / 事件──▶ 渲染层（R3F / three）
                                                              UI 层（React DOM + zustand）
```

### 6.2 插件根目录
```text
frontline_td/
├── plugin.toml / __init__.py      Python 薄壳：声明 static 面板
├── i18n/                          插件元数据 zh-CN / en（有需要时再加）
├── frontend/                      Vite 工程（游戏本体）；tooling/ 仓库检查脚本，eval/ 评估框架
├── static/                        构建产物（入库，CI 校验与源码一致）
├── docs/{design,adr,generated}/
├── AGENTS.md                      CLAUDE.md 等只有一行，指向 AGENTS.md
├── README.md / CONTRIBUTING.md / LICENSE
├── .gitattributes / .gitignore    gitignore 含 node_modules/、.plans/
└── .github/                       frontend.yml（前端检查）、托管的 verify.yml / release.yml（不改）、PR 模板
```

### 6.3 前端目录（功能优先）
```text
frontend/src/
├── core/        branded 类型、实体句柄（ID + 代数）、确定性数学、RNG 流
├── kernel/      模拟基础设施：世界、组件注册、阶段调度、意图队列、事件队列、
│                修正值管线、句柄校验
├── features/<x>/  capture, combat, construction, logistics, movement, pathing,
│   ├── sim/        规则（进 Worker）       production, squads, terrain, units, vision
│   ├── rules/      纯规则，sim 与客户端共用
│   ├── render/     画面
│   ├── ui/         面板
│   ├── content.ts  本功能负责的内容 schema 片段
│   ├── protocol.ts 本功能的命令、事件、快照通道
│   ├── README.md   固定章节：职责 / 公开接口 / 拥有的组件 / 不变量 / 对应设计

├── modes/<mode>/  玩法装配：参与阵营、控制者、开局状态、胜负条件（当前只有 assault）
├── content/     内容数据（建筑、怪物、地图）+ 拼装 schema + 校验
├── protocol/    拼装各功能通道 + 编解码
├── runtime/     Worker 入口、时钟与变速、快照缓冲
├── client/      快照读取与插值、共享节流时钟、三态分离 store（interaction / selection / inspector）、视角与小队/小地图模型、集中会话重置
├── render/      渲染公共设施：画布、镜头、高亮圈层（SelectionHighlightLayer）、线缓冲、单位插值与输入分发
├── ui/          九宫格战术 HUD 外壳（HudShell）、快捷键引导栏、战略小地图、战情检视器与离线原语组件库（kit/styles）
├── input/       键鼠 → 意图 → 命令
├── i18n/        zh-CN / en 文案与类型化取词
├── host/        NEKO 桥接（显示模式；以后接解说）
├── dev/         调试面板
├── testing/     共享测试辅助（仅测试代码可引用，ADR 0043）
└── app/         装配入口：main/App（主线程）、sim-registry + sim-worker（Worker 端）、dispatch（意图路由）、resolve-setup、assault 场景测试
```

### 6.4 依赖规则（dependency-cruiser 强制）
- `core` 不依赖任何内部模块；`kernel` 只依赖 `core`。
- `features/*/sim` 可依赖 `core`、`kernel`、`content`、本功能 `rules`，以及**其他功能 `sim/index.ts` 的公开接口**。
- `features/*/rules` 只依赖 `core`、`protocol` 类型、`content` 类型。这是"客户端不得依赖模拟层"的**有意例外**：用于消除 UI 与 sim 重复实现同一规则（例如可否建造、是否买得起）。
- `features/*/render`、`features/*/ui` **禁止依赖任何 `sim/`**，只能用 `client`、`protocol`、`rules`、`render` / `ui` 公共设施、`i18n`。
- 跨功能引用只能经由 `index.ts`；禁止循环依赖；只有 `app/` 可以装配全部模块。
- `modes/*` 可依赖各功能的公开接口；除 `app/` 外，任何模块禁止依赖 `modes/`（§6.15）。
- `frontend/eval/` 可使用 `src/` 的公开接口；`src/` 禁止引用 `eval/` 与 `tooling/`。

### 6.5 模拟运行时
- 每 tick 50ms 模拟时间；倍速 s 时每秒 20·s 个 tick。
- 每个真实时间片最多补跑 N 个 tick，超出部分丢弃（游戏变慢，避免死亡螺旋）；调试面板显示实际 tick 速率。
- 命令带 tick 编号，在下一个 tick 边界生效。**暂停与变速是运行时状态，不进命令日志**，因为它们不影响游戏结果。
- 主线程保留最近两份快照，按经过时间插值显示。
- 阶段初稿：命令 → 导演 → 指令与 AI → 移动 → 战斗意图 → 结算管线 → 伤亡清理 → 物流 → 建造进度 → 占领与迷雾 → 应用结构变更 → 输出快照与事件。模块把系统登记到阶段，阶段内顺序显式声明。部分系统按 tick 取模降频（例如物流运输每 20 tick 结算一次）。

### 6.6 协议
- 命令、事件、快照通道由各功能在 `protocol.ts` 中定义，`protocol/` 只负责拼装。新增功能 = 新增通道，不修改共用的大类型。
- 快照分三类：
  1. 每 tick 稠密快照（单位位置 / 类型 / 血量 / 状态位）：TypedArray，transfer 零拷贝。
  2. 事件流（开火、死亡、建成、占领、集结预警、命令被拒绝等）：用于特效、通知，将来可供 NEKO 解说。每份快照携带自上次投递以来所有 tick 的事件；客户端维护带序号的事件日志，各消费者用自己的游标读取（ADR 0045）。
  3. 低频或变更时发送：资源与物流摘要、网格层（迷雾、物流覆盖、道路、流场调试）。
- 快照只包含玩家可见的内容（区分真实状态与玩家已知状态）。
- 单位通道从一开始用 TypedArray；其余通道先用结构化克隆，有实测瓶颈再优化。按估算 1 万单位 × 约 32 字节 × 20Hz ≈ 6.4MB/s，暂不需要按视野裁剪。

### 6.7 模拟层内部：部分 ECS
- **ECS（bitecs）**：单位、建筑、弹道等数量多、按组件批处理的实体。组件存储由我们分配 TypedArray；位置用 Float64，送渲染时转 Float32。bitecs 只用实体索引、成员掩码与查询（ADR 0026）。
- **独立模块（非 ECS）**：地形网格、流场服务、空间哈希、物流网（图）、导演（规则集）、小队（指令是数据，单位以小队 ID 关联）。
- 字符串、数组、对象引用类数据放在模块内部结构（以实体句柄为键的表、图结构），不塞进组件。

### 6.8 地形模型
- **格子**：高度层级（整数）、地表类型（陆地、浅水、深水……）、地表修正（减速等）。城墙不是地形，是占格建筑。
- **边**：相邻格是否可通行。悬崖 = 不同高度层级之间的边不可通行（坡道例外）。
- **移动类别**：地面、两栖、海上（以后）、空中……每类一张代价表。寻路按「移动类别 × 体积等级」生成代价场。特殊怪物（如翻墙）通过代价表或"攻击障碍"逻辑表达。
- 视线、射程修正、空地目标可攻击性读取同一张高度网格。
- 只有地形模块知道原始地形编码；其他模块通过其公开的格子 / 边属性与代价场读取。新增地表类型（如海域）≈ 新增类型 + 代价表数据，不改寻路算法。
- 流场按扇区缓存；建造或摧毁阻挡物时只失效受影响扇区，局部重算（尚未实现：体积等级不存在，失效仍为全局清缓存与全图重编号，ADR 0010 实现：部分）。
- 流场之上需要局部避让（分离与推挤），邻居遍历顺序必须确定。

### 6.9 弹道与效果：组合模型
武器 = 正交维度的数据组合，不是"弹道类型"枚举：
- 投送方式：即时 / 光束、追踪且必中（有飞行时间）、抛物线打地面……
- 目标选择：单位、地面点、区域。
- 效果包：伤害类型、范围形状、持续伤害 / 状态效果。

新武器 = 新数据组合；只有新投送方式才需要在战斗模块新增系统。

### 6.10 建造
- 下令即创建建筑实体，挂 `UnderConstruction`（进度）；所需材料作为工地的 `CargoStore`，由物流网按"建造"类别送达（ADR 0025）。实现约定见 [ADR 0029](../adr/0029-construction-implementation.md)：蓝图预订、激活排队、拆除残骸、道路工程分段施工。
- 下令时即占格、挡路、可被攻击；正常运转的系统通过查询排除建造中的实体（`OPERATIONAL_EXCLUDE`）。
- 修复、升级复用同一机制，物流优先级（生命线固定最高，修复、建造、生产可调）自然成立（修复与升级尚未实现，可调优先级只有建造、生产两档）。

### 6.11 修正值管线
Rogue 奖励、前哨加成、相邻加成、补给不足减益、驻防加成等统一走「属性 = 基础值 + 修正值叠加」管线，归 kernel，叠加顺序确定。各功能不得各自实现一套。

实现（M3，约定见 [ADR 0031](../adr/0031-combat-modifiers-inspect.md)）：修正值本身就是组件——`defineModifier(id, stat, op)` 注册一个 `{value: i32}` 的 `ComponentRef`，挂在实体上即生效，由所属模块 `claimWriter` 后用常规组件操作增删写，序列化与销毁清理由组件机制保证。系统用 `ctx.stat(stat, id, base)` 读有效值：加值项求和、基点乘项合成一个钳制到 ≥0 的乘数（`combineStat` 只做倍率合成；目前只有 `MoveSpeed` 一个统计量，战斗尚未经 `ctx.stat` 读修正值，ADR 0043）。`ctx.modifiersOf(id)` 给出按（属性 ID，来源 ID）排序的生效来源。UI 的实体详情走 `Simulation.inspect`：各模块注册只读 inspector 提供分节，内核汇总修正来源与各分节，随快照发往客户端；inspect 不改变模拟状态。

### 6.12 内容与地图格式
- 内容用 TS 数据 + `satisfies` 做类型约束，构建时校验。
- 所有内容属于内容包，本体是包 `frontline_td`，与将来的 mod 走同一条加载管线。内容 ID 为 `包ID:名字`，发布后不改；模拟内部用加载时分配的数字索引，存档只存字符串 ID。修改其他包的内容须写显式补丁（ADR 0022）。
- 对局启动参数 MatchSetup 是回放、存档、无头测试、将来 PVP 的统一开局描述（ADR 0022）。
- 地图格式是契约：地形各层、进攻轴线与出怪点、前哨、初始物流节点，带 `formatVersion`。原型的固定地图按此格式手写；将来的编辑器、生成器、外部工具导入都只是"产出此格式"的来源。
- 局内解锁状态（"本局可用内容"）由占领模块写入，建造、小队模块读取。（存档当前保存 u16 内容索引，与内容版本绑定；包补丁、别名与局内解锁尚未实现，ADR 0014、0022 实现：部分）

### 6.13 客户端
- 渲染层在 `useFrame` 中直接读快照缓冲、更新 InstancedMesh 与缓冲区，**不经过 React state 或 zustand**。R3F 组件只表达结构稳定的东西：地形、建筑分组、灯光、镜头、信息层。`render/` 与 `features/*/render/` 的命令式 Three.js 资源（`BufferGeometry`、`Material`、`CanvasTexture`、`DataTexture`、`LineBuffer`）遵守统一的 `.dispose()` 生命周期，在卸载或容量重建前显式释放（[ADR 0050](../adr/0050-tactical-sandbox-rendering-and-gpu-lifecycle.md)）。
- 客户端状态遵循三态分离（[ADR 0048](../adr/0048-interaction-modes-and-inspector-contract.md)）：`useInteractionStore` 管理平级一级模式（`F1 command` / `F2 build` / `F3 logistics`）与互斥二级工具（`place` / `demolish` / `road`）；`useSelectionStore` 仅持己方可控实体句柄；`useInspectorStore` 持有 `hovered` 与 `pinned`（地形格仅可悬停不可固定，严守迷雾零泄密），并以 `client/inspect-subject.ts` 提供 0ms 观察者快照即时解析与 80ms 防抖强类型 `*Inspection` 深度查询。所有 UI 面板通过共享 `subscribeSnapshotClock` / `useSnapshotValue` 节流订阅快照（禁止自建 `setInterval`），跨局重置收口于 `client/session.ts`。
- 战术 HUD 与离线设计系统（[ADR 0049](../adr/0049-hud-design-system-and-layout.md)）：`HudShell` 采用九宫格流式槽位（无 `position: fixed` 硬编码互盖），集成左上时间/视角/全屏与 `ToastStack`、左中可折叠 `KeyGuideRail`（`K`/`?` 开关、`Esc` 不关闭）、左下模式栏与战略小地图 `Minimap`、底中小队/建造/道路工作台、右上 `StockPanel`（含净速率 `/s`）与默认收起的调试面板（`` ` ``），以及右下 `InspectorPanel`。全部 UI 原语与模式联动主题色收口于 `src/ui/kit/` 与 `src/ui/styles/`，100% 离线零外部字体/图标依赖。
- 输入分三段：按键 / 鼠标 → 意图 → 命令，由数据驱动的 `input/keymap.ts` 按通用层与当前模式分层解析，组件中不直接监听具体按键。
- 建造预览（`GhostPreview`）由客户端依据快照网格层与 `rules/` 先行判断，显示程序化建筑轮廓、连接与服务双圈、武器射程圈及阻塞原因，最终由模拟层裁决；不合法时模拟层发出 `COMMAND_REJECTED` 并由 `ToastStack` 提示。
- 镜头：M2 起就是同一个摄像机在 3D 观战与 2D 正交战术视角之间切换（设计清单 A6 ⑤，[ADR 0028](../adr/0028-rendering-camera-picking.md)、[ADR 0033](../adr/0033-design-checklist-referenced-items.md)），场景从一开始按 3D 构建；F1 阶段按 [ADR 0048](../adr/0048-interaction-modes-and-inspector-contract.md) 改为 `Tab` 键手动切换、取消暂停自动切视角，并在未开启「视角锁定」时于进入 `F2` / `F3` 自动切 2D、返回 `F1` 自动恢复 3D。
- 电子沙盘信息可读性（[ADR 0050](../adr/0050-tactical-sandbox-rendering-and-gpu-lifecycle.md)）：建筑采用程序化多部件轮廓（`visual.silhouette`）与离线 `CanvasTexture` 屋顶战术图标（`visual.glyph`），蓝图（`STATE_BLUEPRINT`）与等待阻塞（`STATE_WAITING`）视觉分离；`UnitsLayer` 显示低电/断电标牌；`SelectionHighlightLayer` 绘制地面四角框、武器射程圈与物流连接/服务双圈；`TerrainMesh` 使用基于 `fwidth` 的自适应网格着色器强化高程、悬崖与坡道对比；`LogisticsOverlay` 服务覆盖层以单张 `DataTexture` 绘制；所有信息层同时以颜色与形状/图案区分，照顾色盲。

### 6.14 Python 薄壳
只声明 static 面板与插件元数据（含 i18n）。将来如接入 NEKO 解说 / 语音，参照 `neko_survivors` 的 `game_event → /chat → speak` 模式，经事件流驱动。

### 6.15 阵营与玩法可插拔
详见 ADR 0019。玩法会变：当前只有攻占模式，其他方向随时可能加入或删掉。目标不是预先支持它们，而是加删玩法时不改通用模块。

**多阵营数据结构（M1 起）**
- 阵营是对局中的一个参与方，中立也是阵营。`core` 提供 `FactionId`；kernel 维护阵营表和关系表（敌对 / 同盟 / 中立），索敌、视野等一律查关系表。
- 属于某一方的状态（资源、解锁、迷雾、物流网、实体归属）一律按 `FactionId` 存储，不存在全局"玩家状态"。
- 实体归属是契约组件 `Faction`，创建时写入、之后不改写；占领通过新建实体表达（ADR 0038）。
- 命令带发出者 `FactionId`，应用前校验权限；快照按观察者阵营生成。
- 按阵营迭代时按 `FactionId` 升序。
- AI 只能通过命令做决策（导演决定集结、进攻方向）；某一方规则自带的机制（巢穴产兵）是模拟层的系统。

**可删除性**
- 玩法专属代码放在 `modes/<mode>/`：参与阵营、控制者、开局状态、胜负条件。通用模块对外提供能力（例如"服务挂了物流组件的实体"），不感知玩法；胜负条件由玩法在装配时提供。
- 只有 `app/` 引用 `modes/`（dependency-cruiser 强制）；模拟代码禁止判断玩法 ID 字面量（lint 强制）。
- 最小注册表测试：不注册任何玩法时，模拟核心仍能运行并通过确定性测试。
- 删除玩法 = 删除 `modes/<mode>/` + `app/` 注册表中的对应行；只被它使用的功能由 knip 发现后一并删除。

**控制者接口在 M1 定下**（MVP 已有本地玩家、导演、策略机器人）：只读本阵营已知信息、输出命令，在命令阶段运行，用专属 RNG 流。

**可开关的机制**是独立的组件 + 系统，由玩法决定注册；**通用规则对各阵营对称**，用镜像地图 + 对调阵营的场景测试检查。

**暂不做**：规则原型、模式各只有一种实现，不搭通用玩法框架，等第二种玩法出现时再提炼（§7.3 第 4 条）。不写联机代码；确定性设计已是锁步联机的前提。物流网按阵营分别存在，模型见 ADR 0025。

## 7. 设计原则

### 7.1 总体
1. **依赖单向流动**，由工具强制。模拟层不知道画面存在，画面不能改模拟状态。
2. **唯一契约**：模拟层与外界只经由协议（命令、快照、事件）交互。
3. **配置驱动**：加内容尽量只加数据。
4. **索引由代码生成，人只写"为什么"**。
5. **目标不是"一次设计正确"，而是"错的地方影响小、改起来便宜，腐化一出现就被发现"**。

### 7.2 模块协作
1. **契约组件**：放在 kernel，数量少、稳定。组件默认归属某个模块，**两个以上模块确实需要**时才升级为契约组件。例：`Faction`、`InWorld`、`UnderConstruction`。`CargoStore` 归 logistics 所有，但任何实体挂上它就会被物流网补充，物流模块不知道塔、小队、工厂是什么——跨模块共享不必进 kernel。
2. **单一写者**：每个组件只有所属模块能写；组件存储不导出，外部只拿 `readonly` 视图（类型层面强制）。
3. **意图 → 结算**：争用状态（血量、资源、格子占用、物流分配）由各系统提交意图，所属模块在固定阶段统一结算。伤害结算是固定顺序管线：基础值 → 修正值 → 抗性 → 护盾 → 血量；新机制以声明方式插入阶段。
4. **事件只通知"已经发生"**：需要答案时调用对方公开查询函数。事件在阶段边界统一处理，处理中产生的新事件进入下一阶段；不递归、不在同一阶段内连锁。
5. **窄查询接口**：跨模块读取经由公开函数，不读对方内部数据。
6. **跨 tick 只保存句柄**（ID + 代数），使用前经 kernel 校验有效性；禁止跨 tick 保存原始实体 ID。

### 7.3 代码
1. **系统按组件查询，禁止判断内容 ID 或"种类"字符串**（lint 强制）。需要特殊行为时新增组件或具名行为，由数据引用。
2. **数据只放参数和组合，行为写在代码里**。配置需要条件逻辑时，在代码中写具名行为并由数据以 ID 引用，不在数据中发明脚本语言。
3. **热路径直接在 TypedArray 上写循环**；kernel 提供类型化视图而不是对象包装。
4. **至少两处真实用法才抽象成共享实现**；不做通用插件注册、依赖注入容器、动态加载。模块注册是显式数组。
5. **底座只做纵向切片真正用到的部分**，每项抽象都要有当前的实际使用者。
6. kernel 改动视同架构级改动，需 ADR（团队成形后加 CODEOWNERS）。
7. 原型期间各功能的公开 API 标记为不稳定；原型评审后冻结边界并写入 ADR。契约组件初始字段最少，接受原型期频繁调整。
8. 替换实现时删除旧实现，不保留并存副本；不留死代码、注释掉的代码、未使用的导入。

### 7.4 典型改动的预期影响范围
写入 AGENTS.md，作为评审时判断"改动是否越界"的基准。

| 改动 | 预期改动位置 |
|---|---|
| 新塔，机制都已有 | 只加 `content/` 数据 |
| 改物流分配算法 | 只改 `features/logistics/sim/` 内部；公开接口不变时其他模块零改动 |
| 新机制（例：切断物流的突袭怪） | 新增 / 扩展一个功能目录（sim / render / ui / protocol）+ 内容数据 + 注册列表一行；物流模块不改（突袭怪挂物流模块公开的拦截组件） |
| 换寻路算法 | 只改 `features/pathing/` 内部 |
| 新地表类型（如海域） | 地形类型 + 代价表数据；寻路算法不改 |
| 新武器组合 | 只加数据；新投送方式才在 combat 新增系统 |
| 新玩法，机制都已有 | 新增 `modes/<mode>/` + `app/` 注册表一行；通用模块不改 |
| 新玩法，需要新机制（例：感染扩散） | 新增功能目录承载新机制 + `modes/<mode>/`；需要第二种控制者或规则原型时先写 ADR 提炼抽象 |
| 删除玩法 | 删除 `modes/<mode>/` + 注册表对应行；knip 报告的孤立功能一并删除；通用模块不改 |

## 8. 跨层功能与执行顺序（已知的固有耦合）
- 一个新机制天然同时涉及规则、画面、界面，这是功能本身决定的。架构保证的是"改动落在可预测位置、每处都是局部修改"，不保证"只改一个文件"。
- 系统执行顺序是全局耦合：顺序表生成进索引；确定性哈希测试捕获无意的顺序变化；调整顺序视为架构级改动。
- 事件让调用链隐式：生成"哪个模块发出 / 消费哪些事件"的索引。

## 9. 确定性规范
- 保证范围：同一构建 + 同一种子 + 同一带 tick 编号的命令序列 → 同一状态（Chromium / V8 内）。
- 纯度区（`core`、`kernel`、`content`、`protocol`、`features/*/sim`、`features/*/rules`、`features/*/content.ts`、`features/*/protocol.ts`，以及 `modes/*/` 中除 `ui/` 以外的部分）禁止：`Math.random`、`Date`、`performance`、DOM 全局对象、超越函数（sin / cos / atan2 / exp / pow 等）。lint 强制。
- 随机数统一使用带种子的 RNG，**按用途分流**（战斗、导演、地图生成等各自独立），避免无关改动改变其他系统的随机序列。
- 模拟逻辑不依赖帧时间差。
- 时间用整数 tick；数量类（资源、货物、血量、伤害）用千分单位整数，统一向下取整；只有几何量用浮点（ADR 0020）。
- 遍历顺序稳定：实体查询顺序、系统顺序固定；排序比较函数不得存在并列不定。
- 渲染层的插值、特效、随机抖动不受限制，不影响模拟。
- 存档用状态序列化，不用回放；回放只用于复现与测试。

## 10. 测试策略
- **黄金状态哈希**：地图 + 种子 + 命令脚本跑固定 tick 数，比对状态哈希。
- **同场景跑两遍一致**。
- **中途存档恢复一致**：跑到一半序列化 / 恢复，与一口气跑完一致（同时保证状态可完整序列化）。
- **场景测试是行为规范**：场景构造器（一小块地图 + 实体 + 命令 → 跑 N tick → 断言）。每个玩法机制必须附带场景测试。
- **代码测试只管正确性**：确定性与状态哈希、场景行为、内容 schema 与引用完整性、运行时不变量（无 NaN、无悬空句柄）、阵营对称性。性能与平衡不写成代码测试，由评估框架负责（ADR 0024）。
- **无头运行器** `runScenario(地图, 种子, 命令序列, tick 数, 探针) → 统计` 由测试与评估框架共用，不为评估另写模拟逻辑。
- 测试直接调用 sim，不经 Worker。
- 浏览器端到端检查由 Playwright 覆盖（[ADR 0041](../adr/0041-governance-and-indexes-v2.md)），包含基础冒烟与 HUD/交互模式/小地图/多分辨率防重叠检查（`e2e/`）；视觉回归（像素/美感）与多局重开显存仍留待以后或人工验证。

## 11. 工程与防腐化

### 11.1 工具链
TS strict、ESLint、Prettier、Vitest、dependency-cruiser、knip、Playwright（浏览器冒烟，仅 Chromium）、棘轮脚本（自写）、gen-index 脚本（自写）、文档检查脚本（自写）。引入新依赖前说明理由；版本优先选择发布满 7 天的版本，不用浮动范围。

### 11.2 CI
`frontend.yml` 三个并行 job（[ADR 0042](../adr/0042-verification-segmentation-parallel-ci.md)），各自 checkout → setup-node（npm 缓存）→ `npm ci` 后只调 npm 脚本，与本地门禁同一份：**static** = `verify:static`（类型检查、lint（含纯度、i18n 字面量）、格式、依赖规则、knip、索引新鲜度、文档检查、棘轮）；**test** = `test`（vitest `unit` + `scenario` 两个 project，全对局/慢测试命名 `*.scenario.test.ts`）；**build** = `verify:build`（构建并校验 `static/` 无差异、包体积 ≤ 32MiB / 24MiB 预警）→ 生成物一致性检查 → Playwright 浏览器端到端检查（`npm run e2e`，含冒烟与 HUD/模式/小地图/防重叠测试，服务真实 `static/` 产物）→ 失败时上传报告。本地 `verify` = `verify:static && test && verify:build`；lint/format/typecheck 有本地缓存（CI 冷跑）。评估运行器（`eval:perf`/`eval:balance`）不进 CI 门槛；`eval/` 下的 `*.scenario.test.ts` 是普通测试，随 `npm run test` 进 CI。插件市场托管的 `verify.yml`（含 `neko-plugin check`）/ `release.yml` 保持模板原样。

### 11.3 防腐化机制
腐化的根源是 AI 追求完成眼前任务，单次合理的改动不断累积。防线设在"累积"这一层：
1. **参考实现**：M2、M3 写成示范代码（movement、pathing、logistics、construction 等）；仓库已有代码是最强的提示词。
2. **棘轮指标**（基线文件 `frontend/ratchet.json` 入库，只许变好）：`asAny`、`tsIgnore`、`tsExpectError`、`eslintDisable` 计数（所有逃生口必须附理由）与 `longFiles` 超长文件数（>800 行计入，(600, 800] 仅警告；测试与 `test-world.ts`、`kernel/testing/` 豁免）。变差即 CI 失败，放宽基线必须在 diff 中显式出现。knip（未使用的导出 / 文件 / 依赖）是另一道独立门禁。
3. **公共接口清单**：`docs/generated/exports.md`（各公共桶的导出名、种类、注释首句）与 `docs/generated/contracts.md`（`Simulation.describe()` 清单：系统、组件写者、消息、通道）自动生成入库；PR 改动接口、kernel、protocol、依赖规则时在 diff 中显形，单独评审（以后配 CODEOWNERS，见 [ADR 0041](../adr/0041-governance-and-indexes-v2.md)）。
4. **场景测试**作为客观验收标准。
5. **先查索引再动手**：AGENTS.md 第一条；PR 模板含"复用了哪些已有抽象，为什么没有复用"。
6. **人工评审聚焦边界**：工具拦得住越界，拦不住"抽象本身错了"。目标是让需要人判断的改动变少且显眼。每个里程碑回顾 ADR，预留重构时间。

## 12. 文档体系

| 类别 | 位置 | 读者 | 生命周期 | 保鲜手段 |
|---|---|---|---|---|
| 入口守则 | `AGENTS.md`（其他工具的守则文件只有一行指向它） | 人与 agent，动手前必读 | 长期 | 长度上限（约 150 行），超出拆分为链接 |

## 14. 已知风险
1. **抽象或模块边界划错**：用功能优先布局、单一写者、意图 → 结算缩小影响范围；原型评审后再冻结边界。
2. **kernel 变成大杂烩**：契约组件准入门槛 + kernel 改动视同架构级改动。
3. **确定性被悄悄破坏**：lint 拦全局调用；三类确定性测试拦遍历顺序、浮点累加顺序等隐蔽问题。
4. **性能**：大量单位的流场寻路与局部避让是热点；分区流场、SoA、Worker、实例化渲染从第一天就位，其余按实测优化。
5. **Worker 调试成本**：调试面板直接查看 Worker 内实体与各系统耗时。
6. **bitecs 更新慢**：封装在 kernel 内，组件存储本就自行分配，替换范围仅限 kernel。

## 附：环境备注
- 插件由 `uv run neko-plugin init frontline_td --type plugin` 创建。
- 在 N.E.K.O 源码仓库的 `plugin/plugins/` 下运行 `neko-plugin check` 时，会误报"插件源码目录没有自己的 git 仓库"：CLI 将内置插件根目录下的插件视为 CI 挂载源码并跳过 git 诊断（`plugin/neko_plugin_cli/commands/release_cmd.py` 的 `_is_builtin_source_plugin_dir`）。插件目录本身是正常的独立仓库。
- 外层 N.E.K.O 仓库的 `.gitignore` 未忽略 `plugin/plugins/frontline_td/`，外层 `git status` 会显示为未跟踪目录。
