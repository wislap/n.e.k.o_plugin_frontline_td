# 0020. 数值、时间与容量约定

- 状态：已采纳
- 实现：已实现
- 日期：2026-11-15
- 决策者：wislap
- 批次：M1 前置
- 领域：模拟

## 背景

单位和数值约定一旦散落在各个模块里就几乎改不回来；浮点累加会产生漂移，影响存档、状态哈希和将来的锁步联机（[ADR 0006](0006-determinism.md)）。kernel 的组件存储与快照缓冲都依赖存储容量策略（[ADR 0009](0009-partial-ecs-boundary.md)）。

## 决策

### 时间
- 模拟内部只用**整数 tick** 计时（1 tick = 50ms，[ADR 0005](0005-fixed-timestep-speed-pause.md)）。
- 内容数据中的时长以秒书写，由内容加载器换算为 tick：四舍五入，最少 1 tick。模拟层看不到"秒"。
- 每秒速率（产量、回复等）在加载时换算为每 tick 的整数量（见下）。

### 几何量
- 位置、距离、速度、射程等用 Float64，单位是"格"；格子 `(x, y)` 的中心在 `(x + 0.5, y + 0.5)`。送渲染时转 Float32。

### 数量
- 资源、补给量、血量、伤害、护盾等**数量一律用整数，以千分之一为单位**（1 单位 = 1000）。每 tick 的小数产出因此可以精确累加。
- 百分比类修正值用**万分比整数**（10000 = 100%）。
- 舍入统一向下取整，由 `core` 提供的整数运算函数实现；各模块不得自行舍入。
- 显示时由客户端换算回单位。
- 组件中的数量字段使用 Int32（上限约 214 万单位）；非 ECS 结构中的数量必须保持安全整数，`core` 的整数运算在开发构建中断言这一点。中间乘积（数量 × 万分比）在安全整数范围内。

### 实体存储容量
- **不设实体数量上限**，也不设任何"性能保险丝"。性能问题从根源优化，依据是评估框架的性能基线（[ADR 0024](0024-evaluation-framework.md)）。
- 组件存储按需扩容：容量用满时，在 tick 边界把存储加倍并整体拷贝。扩容不影响模拟结果，确定性不受影响。初始容量由地图给出提示值。
- 因此**组件视图不能跨 tick 缓存**：系统每个 tick 都从 kernel 重新获取视图。渲染端每次从快照拿新缓冲，不受影响。
- 失控生成之类的 bug 由调试面板与评估框架发现，不用游戏内上限掩盖。

## 后果

- 内容作者用直观的秒和小数书写，换算集中在加载器一处。
- 数量类运算没有浮点漂移；几何类仍是浮点，靠固定的运算顺序与确定性测试保证一致。
- 扩容时有一次性拷贝开销；"视图不跨 tick 缓存"是所有系统都要遵守的规矩。
