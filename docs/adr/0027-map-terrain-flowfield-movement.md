# 0027. 地图格式、地形规则、分区流场与移动的实现约定

- 状态：已采纳
- 日期：2026-11-16
- 决策者：wislap
- 批次：M2 第一个参考实现
- 领域：地形

## 背景

[ADR 0010](0010-terrain-model-sector-flowfields.md) 定了地形模型和分区流场的方向，[ADR 0015](0015-map-format-versioning.md) 定了地图格式要带版本，[ADR 0022](0022-match-setup-content-ids-packs.md) 定了内容 ID 和内容包。M2 第一次把它们写成代码，有一批具体约定会被之后的建造、物流、战斗、导演依赖，需要固定下来。

## 决策

### 内容管线
- 每个功能在 `features/<x>/content.ts` 里声明自己的内容 schema 和类型；本体包的数据放在 `src/content/frontline_td/`，一个注册表一个文件。
- `loadContent()` 一次完成：按 schema 校验、检查 ID 属于本体包且不重复、按完整 ID 排序分配数字下标、单位换算（ADR 0020）、跨注册表引用检查。所有问题汇总成**一个**错误抛出。
- 内容库由调用方持有并传入，不做模块级缓存。

### 地图格式（formatVersion 1）
- `{ formatVersion: 1, id, width, height, legend, rows, points }`：`legend` 把一个字符映射到（地表、高度 0–15、是否坡道），`rows` 是逐行的字符画，`points` 是命名坐标（出生点、敌方出发点）。
- 字符画便于人手编辑和在评审时直接看 diff。将来地图编辑器、更大的地图需要别的编码时，升级 formatVersion，并写迁移。
- 解码后的地形是三张平铺数组：高度（u8）、地表下标（u16）、坡道标记（u8）。

### 地形规则
- 移动类别是内容注册表，M2 只有 `ground`。地表给每个移动类别一个整数代价，**缺省即不可通行**；另有速度修正（基点）。
- 8 邻居边规则：两格都可通行，并且高度相同，或高度差为 1 且**较低的一格是坡道**。斜向一步还要求两条正交腿都可通行，不能切角。
- 步进代价是整数：正交 = 目标格代价，斜向 = floorDiv(代价 × 14, 10)。
- 这条规则放在 `features/terrain/rules/`，模拟和渲染共用。
- M2 的地形是静态的，开局时写入两张全局网格图层 `terrain.height`、`terrain.surface`，客户端从第一份快照拿到。

### 分区流场
- 扇区边长 16 格，每个移动类别一张门户图：
  - 门户 = 扇区边界上双向可通行的相邻格对的最大连续段，每段取中间一对作为门户节点。
  - 扇区内边 = 在扇区内从每个门户格跑局部 Dijkstra 得到的到其他门户格的代价。
- 目标按（格子，移动类别）共享并引用计数，ID 取最小空闲值。目标表随存档保存；门户图、到目标的门户距离、各扇区的流向场都是派生缓存，不存档，恢复后按需重算，结果相同。
- 流向场按（目标，扇区）惰性计算：目标扇区以目标格为种子，其他扇区以边界门户格到目标的门户图距离为种子，在扇区内跑 Dijkstra 得到积分场。每格的方向取**这一步可通行**的邻居中"邻居积分 + 步进代价"最小的那个，并列时按固定顺序 N、E、S、W、NE、SE、SW、NW 取先者。
- Dijkstra 用二叉堆，键为（代价，节点下标），只用整数，结果确定。
- 门户近似会让路径比真正最短路略长。跨 3 个以上扇区的测试里记录了容差：每跨一个扇区最多多出两步跨边代价。
- 失效：`invalidateCells` 重算被改动格所在扇区及其 4 邻扇区的门户和扇区内边，重建门户图，并清空所有派生缓存。M3 的建筑占格从这里接入。

### 移动
- 位置、速度用 f64，单位是格（格 (x, y) 的中心是 x + 0.5, y + 0.5）。IEEE 加减乘除和 `Math.sqrt` 在同一构建下结果确定（ADR 0006 的允许清单）。
- 移动阶段三个系统，按顺序：
  1. **转向**：每个单位朝自己的站位走（见下文"编队站位"）。离站位 8 格以内、并且到站位的格子直线全程可走时，直接朝站位走；否则沿共享目标的流场走，流向为零（已在目标格）时也直接朝站位走。离站位 0.3 格以内算到达，之后进入"守位"状态：被推离站位会自己走回去。不可达时停下。
  2. **分离**：所有单位（含静止的）放入桶大小 2 格的均匀空间哈希，每 tick 重建；按实体 ID 升序遍历，邻桶按固定顺序，桶内按 ID 升序；两个单位的距离小于半径之和加 0.2 格的间隙时，沿分离方向各推开重叠量的一半，所以静止时单位之间留有空隙。推开量**加到速度上**，不直接改位置。
  3. **积分**：新位置 = 位置 + 速度；如果这一步跨到的格子不可达，依次只走 x、只走 y，都不行就原地不动；限制在地图内。转向和分离产生的位移都经过这一步，所以单位不会被挤进岩石或挤下悬崖。
- **编队站位**：移动命令按移动类别分组。每组以目标格为中心，按方形螺旋收集可通行、并且和目标连通的格子作为站位，每个单位一格，不够时循环复用。分配站位时兼顾两件事：落点围绕目标集中，同时保留出发时的相对队形。做法是：把队伍相对中心的偏移按站位分布的大小缩放，得到每个单位的期望点；离中心最远的单位先挑最近的空站位，然后两两交换，直到再没有一对交换能让总距离变小，因此不会出现两个单位的路线交叉。
- `MoveTarget` 是每个可移动单位**常驻**的组件，用 `active` 字段表示状态（空闲、移动、守位），不靠增删组件。原因是增删组件要到 tick 末才生效，同一 tick 内连下两条移动命令会重复申请目标、泄漏引用计数。可移动单位的初始组件由移动模块导出的辅助函数提供，其他模块不逐个引用移动组件。
- 空间哈希目前是移动模块的内部实现。M3 战斗需要邻近查询时再提取成共享设施（architecture §7.3）。
- 移动命令 `movement.move`：不属于发令方或不能移动的单位被跳过，一个都不剩时拒绝；目标格必须在地图内，并且对剩下单位的每个移动类别都可通行。**先全部校验，再修改状态**，被拒绝的命令不会只执行一半。同一移动类别的单位共享一个目标。

### 单位与开局状态
- 单位内容：速度（格/秒，装载时换算成格/tick）、半径、移动类别。
- MatchSetup 的阵营条目增加 `start.units`（ADR 0022 的"开局状态"字段）：开局时在指定点周围按确定的方形螺旋挑选空的可通行格，每格放一个单位。
- 单位位置通过快照通道 `units.dense` 以平铺 TypedArray 发给客户端，按实体 ID 排序（ADR 0004）。M2 全部可见，迷雾在 M5 接入。
- 传输层先复制通道和图层里的 TypedArray，再把副本作为可转移对象发送。kernel 缓存的快照还会被控制者读取，不能把它引用的缓冲区转走。

### 性能基线
- `frontend/eval/perf/movement.ts`：256 × 256 的程序生成地图，N 个单位，每 100 tick 给一批单位重新下达随机目标，跑 1200 tick。
- 本机首个基线（Windows x64，Node 24）：N = 2000 时每 tick 平均 1.04 ms、p95 1.76 ms；N = 5000 时平均 2.71 ms、p95 4.37 ms。最慢的系统是分离（约占八成）；重新下达目标的 tick 因为要分配站位，最长 11 ms（N = 2000）和 16 ms（N = 5000）。基线文件 `eval/baselines/perf-movement.json` 记录机器和 Node 版本。不进 verify，按 ADR 0024 手动运行和比较。

## 后果

- 地图可以在评审时直接读 diff；新增地表类型只加数据。
- 门户近似的误差是已知、有测试约束的；需要更精确的路径时，再考虑在门户段内多放节点。
- 位置用 f64 简化了移动代码；跨构建的逐位一致不在保证范围内（ADR 0006 已经只要求同一构建）。
- 空间哈希、移动分离以后会成为热点，按评估框架的数字优化，不设单位数上限。
