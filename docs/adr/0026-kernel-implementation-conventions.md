# 0026. 模拟内核的实现约定

- 状态：已采纳
- 日期：2026-11-15
- 决策者：wislap
- 批次：M1 模拟核心
- 领域：模拟

## 背景

M1 实现 kernel 时，有一批约定会被之后所有功能模块依赖，需要固定下来：bitecs 用到什么程度（[ADR 0009](0009-partial-ecs-boundary.md)，[ADR 0021](0021-scheduled-effects-entity-relations.md) 把"是否使用 bitecs 关系"留到 M1），按需扩容的存储怎样不让视图失效（[ADR 0020](0020-numeric-time-capacity-conventions.md)），单一写者与事件规则怎样落地（[ADR 0008](0008-module-collaboration.md)），命令 schema 用什么实现（[ADR 0023](0023-grid-layers-groups-commands-rng-runtime-limits.md) 留到 M1），以及"中途存档恢复一致"怎样在 bitecs 之上成立（[ADR 0006](0006-determinism.md)）。

## 决策

### bitecs 的使用范围
- 只用 bitecs 的实体索引（不开版本号）、组件成员掩码和查询（含 `Not`）。不用它的关系、层级、预制体、观察者和序列化。bitecs 不离开 kernel。
- 容纳关系 `ContainedIn` 是普通组件，字段里存容器句柄，不用 bitecs 关系（回答 ADR 0021 的待定项）。
- 组件字段存放在 kernel 自己分配的 TypedArray 中（SoA）。

### 实体与句柄
- 句柄 = 代数 × 2³² + 实体 ID，代数由 kernel 维护，实体被删除时加一。句柄在使用前经 kernel 校验，失效返回空。
- **查询结果按实体 ID 升序**。kernel 缓存排序结果，结构变更应用后失效，因此每个查询每 tick 最多排序一次。遍历顺序只由当前状态决定，与增删历史无关。

### 结构变更延迟到 tick 末
- 创建、删除实体，增删组件都先排队，在最后一个阶段之后、生成快照之前按队列顺序统一应用。创建实体时立即分配 ID 并返回句柄，组件在应用时才加上，查询在此之前看不到它。
- 组件存储只在应用结构变更时扩容（容量翻倍）。因此同一 tick 内拿到的视图不会失效；视图在每次系统运行时获取，不跨 tick 保存。
- 给实体加组件时，先把该组件在这个 ID 上的字段清零，再写入初始值，回收的 ID 不会继承旧数据。
- 任何模块都可以带初始值创建实体（创建是 kernel 操作，不算写入），例如创建时写入 `Faction`。

### 单一写者在运行时强制
- 模块在安装时通过 `claimWriter` 认领组件（网格图层用 `claimLayerWriter`），每个组件只能被认领一次，重复认领在创建模拟时报错并给出双方模块。
- 写入、增删组件必须出示认领时拿到的凭证对象，伪造的凭证在运行时被拒绝。
- 契约组件 `Faction`、`InWorld`、`ContainedIn` 由 kernel 定义，由将来实现对应机制的模块认领。

### 阶段、事件、意图与调度
- 阶段顺序是 kernel 中的固定列表（architecture §6.5 的初稿），调整视为架构级改动。阶段内的系统按注册顺序执行，可以按 tick 取模降频。
- 系统、调度效果、命令处理函数都要声明自己读取（`reads`）和发出（`emits`）的事件与意图，未声明就使用会报错。这份声明也是将来"谁发出、谁消费哪些事件"索引的数据来源（architecture §8）。
- 读取者通过游标拿到自上次读取以来、**已完成阶段**中发出的条目；同一阶段发出的条目要到下一次运行才可见，因此不会在同一阶段内连锁。降频的读取者会拿到累积的全部条目。意图与事件机制相同，但只允许一个读取者，且不进快照。
- 调度效果按（到期 tick、阶段、插入序号）执行，延迟至少 1 tick（ADR 0021）。

### 命令与控制者
- 命令信封 = tick、发出者阵营、类型、载荷。提交时校验类型、载荷 schema、tick 晚于当前 tick、发出者是对局中的阵营；不通过则向发出者发出"命令被拒绝"事件。
- 在第 T 个 tick 的命令阶段，按（发出者阵营升序、提交序号）应用 tick 为 T 的命令，然后运行控制者。
- **命令日志记录所有来源被接受的命令**（本地输入、AI、脚本）。回放时关闭控制者，直接喂入命令日志。
- 控制者的输入是该阵营在上一 tick 末的观察者快照和它专属的 RNG 流，发出的命令在下一 tick 生效（ADR 0019）。本地玩家也是一个控制者，只把输入队列里的命令交出去。

### 快照
- kernel 生成的快照是**完整的观察者视图**：所有快照通道的值、上一 tick 中该阵营可见的事件、该阵营可见的全部网格图层（按引用，只读）以及本 tick 变化过的图层列表。kernel 不保存任何差量状态，控制者在存档恢复前后看到的输入完全一致。
- "只发送变化的部分"是运行时传输层的优化：Worker 只把变化过的图层复制发给主线程，主线程用上一份快照补齐。

### 存档恢复
- 只在 tick 边界序列化：实体索引、代数、各存活实体的组件与字段值、事件日志与游标、调度队列、RNG 状态、网格图层、待执行命令与命令日志、各模块的非 ECS 状态。状态哈希 = 序列化结果的规范哈希。
- 恢复时只用 bitecs 公开接口复现实体 ID 的回收顺序：先创建 `maxId` 个实体，再按保存的空闲列表**倒序**删除已死亡的 ID，使下一次分配到的 ID 与原来一致；存活部分的内部顺序不影响后续分配。随后按 ID 升序恢复组件。

### 命令 schema 与共享类型
- 命令 schema 用 `core` 中自写的小型 schema DSL：TS 类型与运行时校验从同一份定义派生，对象不允许多余字段，不做类型转换。不引入第三方库，因为模拟层和 `protocol` 不能依赖 npm 包（ADR 0007 的依赖规则）。
- 命令、事件、意图、快照通道的描述符，以及主线程也要用的类型（`Snapshot`、`CommandEnvelope`、"命令被拒绝"事件）放在 `core`，客户端不必引入 kernel。

### 无头运行与计时
- `runScenario` 位于 kernel，测试与评估框架共用（ADR 0024）。
- 按系统计时的计时函数由调用方注入；kernel 自己不调用 `performance`，纯度规则不受影响。

## 后果

- 新实体从下一个 tick 起才出现在查询中，伤亡也在 tick 末才真正移除；同一 tick 内的状态因此稳定，系统可以放心遍历。
- 查询排序与结构变更队列有固定开销，由评估框架的性能基线衡量，有瓶颈再优化。
- 恢复存档依赖 bitecs 0.4.0 实体索引的回收行为；升级 bitecs 时，"中途存档恢复一致"测试会发现行为变化。
- 事件声明让模块之间的依赖可以生成索引，代价是新增事件时要多写一处声明。
