# 0024. 评估框架：性能基线与数值平衡

- 状态：已采纳
- 实现：已实现
- 日期：2026-11-15
- 决策者：wislap
- 批次：M1 前置
- 领域：工程

## 背景

性能和平衡都需要持续测量，但它们不是"正确性"：把平衡关系写进 CI，数值每调一次测试就失败，大家会习惯性地放宽阈值；性能阈值在共享 CI 机器上也不稳定。用游戏内上限（"性能保险丝"）掩盖性能问题是回避根源。MVP 包含无界面对拍工具与 4 个策略机器人（《设计决策清单 v2》A6 ⑥）。

## 决策

### 代码测试与评估的分界
- **代码测试只管正确性**：确定性与状态哈希、场景行为、内容 schema 与引用完整性、运行时不变量（位置不为 NaN、没有悬空句柄）、阵营对称性。它们是 CI 的通过门槛。
- **评估框架管性能与平衡**：测量、比较、出报告，不作为 CI 的通过门槛。平衡关系（例如"资源源点出口容量 ≥ 终局产出 × 1.2"）只在评估框架里计算，不写成代码测试。

### 位置与依赖
- 评估框架放在 `frontend/eval/`，跑在 Node 中，与 `tooling/`（仓库卫生）和 `src/` 内的测试分开。
- `eval/` 可以使用 `src/` 的公开接口；`src/` 禁止引用 `eval/`（dependency-cruiser 强制）。
- 评估与测试共用同一个无头运行器 `runScenario`，**不为评估另写一份模拟逻辑**。

### 性能部分
- 一组固定的大规模场景，记录每个系统的耗时、每 tick 总耗时、内存，与基线比较并输出报告。
- 默认在基准机器上运行，作为迭代优化的依据；性能问题从根源优化。
- M2 有单位移动后加入第一个场景并建立基线。

### 平衡部分
- 无界面对拍工具与策略机器人：批量跑无头对局，统计胜率、经济曲线、对局时长等；以及数值计算工具。
- 策略机器人就是 [ADR 0019](0019-factions-and-pluggable-modes.md) 的控制者，只通过命令行动。M4 落地。

### M1 预留的钩子
- 调度器按系统计时，生产构建中可去除。
- 探针接口：只读地读取统计数据，供评估与 `runScenario` 使用。

## 后果

- CI 保持稳定，只因正确性问题失败；性能与平衡有独立的、可迭代的数据来源。
- 基线数据的存放方式（入库或作为产物）在建立第一个基线时决定。
