# 0061. 文档抽象层级与调参记录约定

- 状态：已采纳
- 实现：已实现
- 日期：2026-11-22
- 决策者：wislap
- 批次：治理
- 领域：工程

## 背景

F1–F5、R1–R2、S1–S3、P1–P5 批次的文档与代码同步得很及时，但写得太细：

- ADR 0052–0059 在一天内连续互相部分取代，正文大量记录调参常数（让路权重、
  前瞻距离、惯性系数等）。每调一次参数就要新写一篇 ADR，并且已经出现不一致：
  ADR 0058 记录的桥前收窄斜率是 `1.25`，代码已改为 `0.7`。
- 功能 README 和 `architecture.md` 把算法步骤与常数抄成文字（单行最长超过
  1000 字符），与 [ADR 0046](0046-doc-consistency-conventions.md)"README 写用途，清单交给生成索引"的方向相反，
  也让读者分不清哪些是必须保持的约束、哪些只是当前取值。
- 人工验收清单只写在被 git 忽略的 `.plans/` 里，其他协作者看不到。

## 决策

1. **ADR 记决策，不记调参。** ADR 写选了什么机制、放弃了什么、为什么、带来哪些
   约束。数值只在本身就是决策的一部分时出现（如 tick 50ms、净空分两档）。
   调整已有参数不新写 ADR：常数在代码里命名并注释用途，原因写进提交信息，
   黄金哈希变化照常说明。还在试验的方案先写在 `.plans/`，定型后再写 ADR。
2. **功能 README 写职责与约束。** 「不变量」一节只写必须成立、可以核对的规则
   （谁写哪个组件、结算顺序、确定性要求、失败时的行为），不写算法步骤和常数取值。
   由 `check-docs` 校验：功能 README 不超过 80 行，单行不超过 200 字符。
3. **`architecture.md` 是总览。** 只写模块职责、数据流和对应 ADR 的链接，不写参数。
4. **根目录 README 的操作说明面向玩家**：用玩家能看懂的话写按键与操作，不出现内部
   组件名。
5. **人工验收项写进 `architecture.md` §1.4**，负责人确认后在原条目注明结论与日期，
   不只放在 `.plans/`。

## 后果

- 调参不再牵动 ADR、README、总览三处文档，文档与代码不一致的机会减少。
- 查具体取值要读代码；为此调参常数须集中命名，不在函数体内写裸数字。
- 存量 ADR 0052–0060 的正文不改（ADR 正文不可修改），其中的参数视为当时的取值记录，
  以代码为准。
