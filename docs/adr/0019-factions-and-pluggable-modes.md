# 0019. 阵营模型与玩法可插拔

- 状态：已采纳
- 实现：已实现
- 日期：2026-11-15
- 决策者：wislap
- 批次：M1 前置
- 领域：架构

## 背景

当前版本只做攻占模式：敌方（怪物）已经发育好，玩家从基础起步，推进并攻破要塞；参与方是我方、怪物、中立三方。以后可能出现的玩法方向包括：与其他玩家 PVP、和玩家同规则从零发育的对称 AI、敌人只会扩散的感染模式。这些方向都不是承诺，随时可能加入，也可能删掉（[game_design.md §4.9](../design/game_design.md)）。

架构要满足的不是"预先支持这些玩法"，而是**加入或删掉一种玩法时，不需要改动通用模块**（[architecture.md §4](../design/architecture.md) 诉求 7）。

几种方向在四个维度上变化：谁做决策、用哪套规则、开局状态、胜负条件。现阶段每个维度都只有一种实现。

## 决策

### 现在就落实的数据结构（M1 起）

1. **阵营**是对局中的一个参与方，中立也是一个阵营。`core` 提供 branded 类型 `FactionId`；kernel 维护阵营表和阵营关系表（敌对 / 同盟 / 中立），"谁打谁、谁能看见谁"一律查关系表，不比较具体阵营。
2. **属于某一方的状态一律按 `FactionId` 分开存储**：资源、解锁、迷雾、补给网络、实体归属。禁止出现全局的"玩家资源""玩家迷雾"一类单例。
3. **实体归属**是 kernel 的契约组件 `Faction`。创建实体时写入；之后只有占领模块可以修改。
4. **命令带发出者的 `FactionId`**。模拟层在应用命令前校验发出者有权操作目标，无权时发出拒绝事件。
5. **快照按观察者阵营生成**，只包含该阵营已知的内容。原型只有一个本地观察者。
6. **所有按阵营迭代的地方都按 `FactionId` 升序执行**，保证确定性。
7. **AI 只能通过命令行动。** 决策（例如导演决定何时集结、往哪进攻）通过与玩家相同的命令入口提交，接受相同的校验；某一方规则自带的机制（例如巢穴产兵）是模拟层的系统，不是 AI 决策。

### 可删除性的规矩

1. **玩法专属的代码放在 `frontend/src/modes/<mode>/`**：哪些阵营参加、各自由谁控制、开局状态、胜负条件。当前只有 `modes/assault/`（攻占模式）。
2. **依赖方向**：`modes/*` 可以使用各功能的公开接口；`core`、`kernel`、`features/*`、`content`、`protocol`、`runtime`、`client`、`render`、`ui`、`input` 禁止引用 `modes/`；只有 `app/` 装配玩法。dependency-cruiser 强制。
3. **通用模块对外提供能力，不感知玩法。** 例如补给模块服务"挂了补给组件的实体"，不服务"开荒公司"。胜负条件由玩法在装配时提供，不写在核心里。模拟代码禁止判断玩法 ID 字面量（lint 强制，与"禁止比较内容 ID"同一条规则）。
4. **最小注册表测试**：不注册任何玩法时，模拟核心仍能启动、推进 tick 并通过确定性测试。玩法逻辑一旦写进核心，这个测试就会失败。
5. 删除一种玩法 = 删除它的 `modes/<mode>/` 目录 + `app/` 注册表中的对应行；只被该玩法使用的功能由 knip 报告为未使用，随后一并删除。
6. **可开关的机制必须是独立的组件 + 系统**，由玩法决定注册与否（例如某个玩法关闭单位的"组织度"）。禁止在系统内部按玩法写"跳过"分支。
7. **通用规则对各阵营对称**：占领、收入、据点等逻辑不写成"玩家攻占敌人"这类单向形式，任何阵营都可以占领、被占领、自建据点。用镜像地图 + 对调阵营的场景测试检查对称性（这是正确性测试，不涉及平衡）。

### 控制者接口（M1）

MVP 已有本地玩家、导演、多个策略机器人，控制者接口在 M1 定下：
- 控制者只能读取本阵营已知的信息（导演是否例外在 M4 决定），输出命令；不能直接修改状态。
- 在命令阶段运行；需要随机时使用自己专属的 RNG 流，保证确定性。
- 无头运行时直接调用，不经过 Worker；本地玩家的控制者只是把输入队列中的命令交出去。
- 将来的外部控制者（远端玩家、经宿主桥接的自然语言指令）是异步到达的命令来源，同样在下一个 tick 边界生效并写入命令日志。

### 暂不做的

- **不搭通用的玩法框架。** "规则原型""模式"现在各只有一种实现，按 [architecture.md §7.3](../design/architecture.md) "至少两处真实用法才抽象"，等第二种玩法真正出现时再提炼接口。
- 不写任何联机代码。

## 后果

- 原型只有攻占模式，但从 M1 起数据结构就是多阵营的，成本主要是所有阵营相关的接口都多一个 `FactionId` 参数。
- 已定的确定性设计（命令带 tick 编号、禁用超越函数、RNG 分流、状态哈希测试）正是锁步联机的前提；将来做 PVP 时不需要推翻模拟层。锁步模式下每台机器都持有完整状态，存在透视作弊风险，届时另写 ADR。
- 补给网络按阵营分别存在；补给的具体模型（单一补给量还是多种物资）待定，另写 ADR。
- 新增玩法需要第二种规则原型时，提炼抽象属于架构级改动，需要 ADR。
